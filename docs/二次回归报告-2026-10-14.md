## 三、<span id="backend-details">恢复、职责与审计的交叉问题</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 3.1、<span id="restore-retry">恢复后已处理授权请求重新执行</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

B01 使用真实加密文件备份及新目录恢复。先备份，再停用客户、重新启用客户；恢复后账号正确保持 active／授权版本 3。管理员重新登录并重试原停用请求，HTTP 200 将其再次改为 disabled／版本 4，新增一次状态变更审计。同样，客户经办人交接出去再交回，恢复本应保持当前联系人；重试第一次交接后却再次变为原接替人。

原因是当前授权和审计被合并，但最新已消费的请求键没有合并。应为授权操作保留最新已处理意图，按当前权限安全重建结果或明确拒绝旧结果；不得再次执行旧授权修改。同时设计业务回到备份点、资源不存在与请求键保留之间的合同，避免只合并全部键后静默吞掉未恢复的业务事实。验收应覆盖两种授权变化、跨恢复的同键／异内容冲突及不存在资源的拒绝。

B02 的前提是最新加密来源中账号状态字段缺失或为空，并非篡改密文绕过加密。恢复只确认 accounts 是数组，启动也没有验证账号状态；登录、鉴权与写事务采用“不是 disabled 即可”的判断，读取另有 active 白名单，造成不一致。实测非法状态管理员仍能执行停用客户写入。应在来源合并与启动时校验完整账号约束，并统一要求明确 active；兼容迁移必须有明确版本边界。

两项复现见 [恢复诊断源码](./二次回归证据-2026-10-14/restore-cross-scenario_test.go) 与 [日志](./二次回归证据-2026-10-14/supplemental-go.jsonl)。

### 3.2、<span id="field-write">隐藏字段的写入与余项责任人</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

B04 在已有内部备注的工单上，QC 读取结果为留空备注；随后更改客户说明并提交空 remark，后台确实把原内部备注清空。读取脱敏并不能替代写入字段权限。应明确分字段更新合同：没有字段权限时拒绝更改或保持原值；网页也不应让隐藏值参与整组替换。管理员的明确清空仍需保留，不能用“所有空值都忽略”处理。

B05 的财务余项在 QC 视图中不存在，但提交正确 obligationId 后其 Resolved 变为 true。复现需要已知有效 ID，不表示 ID 可随意猜中；服务端仍必须检查责任人或明确的管理角色授权。应为办妥操作统一校验责任人，并记录操作者及依据，覆盖本人、他人、管理员、调度与隐藏余项的请求。

两项已用 [职责诊断源码](./二次回归证据-2026-10-14/permissions-cross_test.go) 的错误行为断言确认；这些用例 PASS 代表缺陷成功复现。

### 3.3、<span id="replay-audit">幂等重试成为未审计的完整读取</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

B03 先通过 HTTP 完成工单写入，再由财务新增内部成本；令后续持久化失败。普通 GET 详情返回 500，但完全相同路由、请求键和请求字节的 POST 重试返回 200，包含原成功响应之后新增的内部财务标记，没有新增读取审计。调用者仍是有权读取的管理员；缺陷是完整资料释放绕过既有审计失败拒绝边界。

应区分“不重复执行业务”和“安全释放重建资料”：返回当前完整工单时，按完整读取保存必要审计；也可设计不暴露新增资料的最小重试结果，并同步网页合同。审计失败时应拒绝完整资料，业务版本、款项、库存仍不能重复变化。

证据为 [精确重试日志](./二次回归证据-2026-10-14/replay-read-audit.jsonl)。诊断初稿曾因请求字节不一致得到 409；修正为逐字一致后确认 200 和新增内部资料。该初稿结果不用于证明审计防护有效。

## 四、<span id="frontend-details">网页异步请求的一致性</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

F01：提交账号状态表单后关闭它，再打开新建工单。旧状态请求成功到达，只检验身份 epoch，随后关闭共享 formDialog。应给每个表单实例稳定标识；回包只处理发起该请求的表单。业务已经成功时可以提示结果，但不能关掉新表单或清空新输入。

F02：实际页面登录管理员，打开 wo_ready 完整详情；同源代理只延迟下一次详情 GET 约 1,200 毫秒。点击编辑备注后，关闭详情并进入现金与票据；迟到响应仍打开备注表单。测试超时为 15,000 毫秒，响应在超时前到达，排除了超时／离线回退的解释。应给办理请求记录视图、所选工单与交互序号；关闭详情、切换视图或发起其它动作后取消旧交互意图。

![已切到现金与票据，旧备注表单仍弹出](./二次回归证据-2026-10-14/browser-late-detail.png)

F03：配置 A 的 POST 成功后，bootstrap 暂挂；配置 B 的 POST 也成功，但 refresh 因 loading 提前返回，没有使 A 的请求失效。A 的旧响应随后覆盖页面 data.settings，后台已是 B。应使用刷新序号与待刷新队列，或成功写入后使旧读取失效，再启动最新刷新；不能把正在加载视为可以丢弃后一次刷新。

F01、F03 已由加载实际 app.js 的可控响应测试确认；F02 同时有真实浏览器证据。VM 诊断不代替所有实体浏览器场景，后续修复需保留确定时序测试并重测真实交互。
