## 🔥 <span id="前言">前言</span>

本清单登记当前仍需处理的 17 组 P2：后端 4 组、维修工作台网页响应保护 3 组、维修工作台独立演示 10 组。状态均为未修复，验收复测未执行。编号按问题维持稳定，不按失败断言数量拆分。

问题定位见 [代码地图](../../代码/README.md#unit-code-maps)，业务依据见 [产品需求](<../物业设备维修服务平台PRD/物业设备维修服务平台 PRD V3.8（Jobs规范版）.md>)与 [接口合同](../../代码/后端/README.md#api-contract)。用例执行及验收门槛见 [测试与验收](../../测试/测试与分级验收/测试与分级验收.md)。责任人、期限及放行结论没有确认信息时保持空白。

## 一、<span id="backend">后端业务问题</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 编号 | 复现条件与当前表现 | 预期与影响 | 实现定位与需求依据 |
| --- | --- | --- | --- |
| B01 | 普通 `POST /orders` 携带不存在、同企业未验收或跨企业父单的 `originalOrderId`，仍创建并保存工单 | 新建接口应核对父单存在、权限及返修资格；否则污染返修关联。该问题不等于能够读取原单 | [actions.go](../../代码/后端/后端代码/internal/workbench/actions.go) 的 `createOrder`／`newOrder` 与 `act/rework`；需求的返修关联与有效验收条件 |
| B02 | 合法创建免费返修子单，完成受理、检测，提交金额为 0 的完整报价；API 返回 `422 invalid_amount`，网页报价表单也拒绝零价 | 有效免费返修应走零价报价确认链，保留免费范围和依据；不能用虚构收款代替 | [actions.go](../../代码/后端/后端代码/internal/workbench/actions.go) 的 `act/quote`／`amount`；[app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `showAction`／`amountField`；需求 A39 |
| B03 | 客户提出异议或拒绝验收，跨过原截止日；调度仅将异议标为解决、仍待客户复验，再扫描自动验收，立即沿原截止日验收并起保 | 异议解决后应有可追溯的验收窗口恢复规则与客户确认依据；避免客户尚未复验便消耗质保期 | [actions.go](../../代码/后端/后端代码/internal/workbench/actions.go) 的 `issue`／`resolve_issue`／`review_acceptance`，以及 [inventory.go](../../代码/后端/后端代码/internal/workbench/inventory.go) 的 `autoAccept`；需求的验收窗口与协商例外 |
| B04 | 当前报价已签署且维修、质检完成，交付时间填为早于工单创建和当前签署的日期；仍保存，并可自动验收为已过期质保 | 交付时间应符合本单生命周期；有依据的补录需明确授权与依据。避免错误日期跳过验收窗口 | [actions.go](../../代码/后端/后端代码/internal/workbench/actions.go) 的 `deliver` 与 [inventory.go](../../代码/后端/后端代码/internal/workbench/inventory.go) 的 `autoAccept`；需求的合并确认和交付验收条件 |

B03 负责暂停与恢复的状态规则，B04 负责时间输入的一致性，分别处理和验收。

## 二、<span id="frontend">维修工作台网页响应保护</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

以下场景使用结构异常或上下文错误的成功响应，范围限于 `代码/前端/PC端/Web/维修工作台` 的客户端保护。不能据此认定正常服务端正在泄露资料、重复入账或允许越权；Web 管理后台是独立实现，需分别验证。

| 编号 | 复现条件与当前表现 | 预期与影响 | 实现定位 |
| --- | --- | --- | --- |
| F01 | 以新意图提交版本 8 的备注，返回结构合法但版本仍为 8 或退到 7、备注仍旧的 2xx，页面仍提示成功并释放请求键；返修响应为原单本身也提示创建成功 | 普通新动作应校验版本推进；返修须新 ID 且父引用正确。未知结果重试应核对同键结果。否则可能误报成功并丢失意图 | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `validateResponse`／`mutateOrder`／`releaseFormKey`；接口合同的动作上下文与幂等要求 |
| F02 | 导出响应结构合法，但 actor 的 ID、角色、企业或授权版本与当前认证身份不符，仍生成 JSON 下载并提示授权导出成功 | 导出需匹配当前认证身份及会话代次，避免采用错误归属资料；正常同身份导航不应被误拒绝 | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的导出处理、`sameSessionActor` 与 `validateResponse`；接口合同的身份锚点要求 |
| F03 | 现金记录缺金额、金额为 null、缺 ID 或方向非法，仍按真实台账使用；缺金额显示为 0，非法方向按正向计算；浅层 Loan 写响应也提示成功 | 采用响应前校验现金 ID、整数金额、收退方向与完整库存响应；不完整资料不得进入金额展示或关闭表单 | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `validOrderRecords`／`validLoan`／`validateResponse` 与现金、借还表单；接口合同的嵌套完整性要求 |

F01 的正常幂等响应可比请求高多个版本，不应强制只能加一。F02 的身份匹配与迟到响应隔离均需覆盖。

## 三、<span id="demo">维修工作台独立演示问题</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

以下场景只涉及合成演示台账。服务端对应规则应单独执行正反对照，演示放行不等于真实服务端放行。

| 编号 | 复现条件与当前表现 | 预期与影响 | 实现定位 |
| --- | --- | --- | --- |
| D01 | 仓库身份自行将借用转耗用、处置或独立跟踪，解除对应阻塞数量 | 这三类批准动作按当前 API 限管理员；演示应保持相同岗位边界 | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `renderInventory`／`loanAction`；对照后端 `inventory.go/loanAction` |
| D02 | 已完结单不经重开便添加借用或客户异议，产生未清义务，状态仍为 completed | 新增义务前应重开并复核；避免完结状态与欠项不一致 | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `available`／`globalForm`，以及 [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的 `apply/issue`／`refreshOrder`；需求 A41 |
| D03 | 没有关联 `orderId` 的独立借用仍可转维修耗用并减少尚欠 | 耗用须有可归属的维修工单；对照后端 `order_required` | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `loanAction`；后端 `inventory.go/loanAction` |
| D04 | 借用责任人表单提供财务等角色，选择后演示仍扣库存借出 | 表单与演示应符合当前 API 接受的有效工程师账号范围；不将此实现约束扩成未来全角色借用禁令 | [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `globalForm/loan`；后端 `inventory.go/createLoan` |
| D05 | 原净核实 500 元，登记并核实 501 元退款后，净实收变为 -1 元 | 超过可退净收款应原子拒绝，金额不能变为负数 | [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的 `apply/verify_cash`；后端 `actions.go` 的 `refund_exceeds_receipts` |
| D06 | 退款核实后未完成内部交接，按真实净额调整应收，演示缺项为空且可完结 | 所有已核实现金，包括退款，均应按约定完成交接后才可完结 | [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的 `derive` 现金交接检查；后端 `service.go/refresh`；需求 A37 |
| D07 | 重复有效票号、无需开票约定或普通文字原件仍能登记发票 | 核对票号唯一性、开票约定和有效原件类型；三种输入归同一登记守卫问题。使用有效 PDF 另测唯一与重复票号以隔离原因 | [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的 `apply` 发票分支及 [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的发票表单；后端 `actions.go`／`invoiceFiles` |
| D08 | 文件有效且资料已制作，接收对象留空仍形成已发送事实 | 发送事实必须包含接收对象；对照后端 `document_recipient_required` | [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的资料发送分支及 [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的发送表单 |
| D09 | 已验收或已确认不能修的单据仍可按取消停止，覆盖已有履约结果，原质保信息仍保留 | 已有终局结果不得直接覆盖；后续更正按重开及结果约束办理 | [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的终局动作与 [app.js](../../代码/前端/PC端/Web/维修工作台/app.js) 的 `available`；后端 `outcome_exists`；需求 A39／A41／A43 |
| D10 | 合法报价阶段总价 100 元、预付款 200 元且未约定先款，演示仍保存报价 | 所有报价均应限制预付款不超过总价；未约定先款只影响开修门槛，不取消金额合法性校验 | [data.js](../../代码/前端/PC端/Web/维修工作台/data.js) 的 `apply/quote`；后端 `actions.go` 报价校验 |

维修仅在 `quote.startRequiresPrepayment=true` 时核实约定预付款后开修；缺省 false。现款销售继续按冻结报价核实全款。处理 D10 时应保持这项业务约定。
